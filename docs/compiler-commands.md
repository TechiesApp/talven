# Pollable bounded compiler commands

Status: implemented reference command primitive under [Proposal 0023](proposals/0023-pollable-compiler-commands.md). It is a cancellation/observation foundation for later [object-reuse watcher integration](object-reuse.md); ordinary build/dev remain unchanged. Prepared-unit and object-build APIs still run synchronously through the compatibility wrapper.

`talven.c_command.BoundedCommand` owns one trusted command's POSIX process group, temporary stdin file, output pipes and readiness selector. Constructing it launches the command. `poll()` defaults to a non-waiting readiness check and returns `None` while pending, or exact stdout bytes after successful EOF and child exit. Empty stdout `b''` is a completed result, distinct from pending. `close()` cancels/cleans up the owned group, and context-manager exit calls it. Cleanup is idempotent. A successful terminal poll can return its retained result again; polling a cancelled/failed closed command is a usage error.

The synchronous `run_bounded` wrapper repeatedly polls with a maximum 10 ms readiness wait, preserving the existing preparation/build result and diagnostic behavior. `poll(wait=...)` accepts 0–10 ms. Each call reads at most 64 KiB total from ready stdout/stderr in chunks no larger than 32 KiB. Thus compiler output cannot cause one caller tick to drain an arbitrarily large stream. No source observation is performed by this primitive: a future watcher must poll its source between command steps and cancel superseded work.

The constructor accepts one nonempty argument list, bytes/bytearray input, a copied environment, optional captured working directory, command timeout and stdout limit. It does not interpret a shell command string. Input and stdout limits are 16 MiB; stdout can be restricted to zero, and stderr is bounded to 64 KiB. Timeout must be finite within (0, 60] seconds, allowing a small remainder of an enclosing aggregate build deadline. Expiry is checked on polling. Usage errors occur before launch where possible. Input/output overflow, timeout or nonzero child status returns `E0402`; unavailable POSIX support or launch/I/O errors return `E0901`.

EOF and direct-child exit are both necessary for success. A descendant retaining a pipe keeps the operation pending, even after its leader exits. Inspect exit with the established non-reaping `waitid` helper, retaining the leader's PID/process-group identity until cleanup. On completion, command failure, polling interruption or explicit close: send TERM, wait up to 100 ms for the direct child, then send KILL to its group and reap the direct child. Descendants receive no separate grace period. Close all pipes, temporary input and selector. Tests verify cleanup of TERM-resistant descendants even when the leader exits first.

Default readiness polling does not wait for process completion, but creation, regular-file I/O, process startup and cleanup remain synchronous. Closing/failing/completing can spend the direct-child grace period; these limits are not hard real-time CPU, disk or memory quotas. Polling must continue for timeout enforcement; callers abandoning a live operation must close it. Uncatchable termination, host failure and descendants escaping their groups remain outside cleanup. The API accepts trusted executable requests, not a sandbox or an authority granted by source/receipts. Tests use Python process doubles; they do not add Talven subprocess/lifecycle language APIs.

Six focused tests verify pending observation opportunities, exact stdin/environment/directory behavior, multi-buffer byte draining under per-poll budgets, empty success, failures/timeouts, explicit cancellation, unreaped leader identity and descendant cleanup. Existing prepared-unit and object-build tests exercise real C compilation/linking and reused borrowing with sanitizers through the wrapper. No watcher native reuse, state preservation, readiness or speed improvement is claimed by this primitive.
